# 双采集机计数器批次交接（Ridgeline 临时库复核）

## 0. 结论先行（给接班人的决定）

**先提交采集机 a 的两个已校时点上看板，采集机 b 整批暂缓，等校时记录。**

理由（均由本目录复放脚本在真实 Ridgeline 临时库上验证）：

1. a 的偏差已确认（本地比真实快 400 ms），其真实时间戳 600、1600 在本轮 now=1700、
   watermark=1000、floor=400、lateness=700、future=100 下**必定可提交**，不依赖任何猜测。
2. b 的偏差未知（-300～300 ms 区间）。**不能把任何猜出来的时间写进可直接提交的请求**：
   把 a 与猜测的 b 捆在一个原子请求里（方案 B），一旦 b 的某个点越界，
   **整个请求 409，连同本来确定可入库的 a 点一起全部失败**（实测 δ=101、300 时可见点为 0）。
3. **先提交 a 的真实代价（如实记录）**：a 提交后 watermark 从 1000 推进到 1600，
   迟到准入线从 300 收紧到 900。b1 的可行真实时间最大只有 800 < 900，因此**一旦先提交 a，
   b1 在本轮无论后来校时结果如何都无法补入**。反事实地说，若此刻就已知 δ_b 且 δ_b∈[-100,100]，
   把 a、b 放在 wm=1000 的同一个原子请求里，b1（t∈[400,800]）本是可以准入的——这就是题目所指
   "抢先发 a 可能让原来还能补的点被拒绝"的那个点。但该同批方案在当前信息下不可执行：
   b 的时间戳未知，不能猜；且实测 δ_b 一旦落在 [-100,100] 之外，捆绑请求会整批 409，
   连已确认的 a 点一起丢掉（方案 B：δ=101、300 时 b1 撞 floor，δ=-300、-101 时 b2 撞未来容差，
   四种情况可见点均为 0）。
   b2 不受此影响：a 提交后它仍可在 δ_b∈[-100,300] 时用单点请求补入（见第 2、3 节）。
4. 等待方案的代价也要写明：等校时记录会推迟看板更新；等待期间若有人推进 retention，
   floor 一旦超过 b1 的实际真实时间，b1 会因保留边界独立死亡，与是否先发 a 无关。
   综合"不能猜时间"这一硬约束，先发确认的 a、暂缓 b 是风险最小的安排，
   但必须在交接中显式登记 b1 的不可补条件，而不是掩盖这个取舍。
5. a 单独入库后，计数器序列只有 2 个点，rate 可计算但**只能标为临时/未对账**，
   正式 rate 须等 b 校时记录到达、合并后再发布。

## 1. 场景参数与口径（全部对应源码语义）

| 项 | 值 | 源码依据 |
| --- | --- | --- |
| 本轮提交 now | 1700 | 请求体 `now`，准入基准 |
| 已提交 watermark | 1000 | `internal/engine/ingest.go`：仅当点时间 > watermark 才推进 |
| 保留边界 retention_ms / floor | 600 / **400** | `policy/admit.go`：`p.Time < n.Floor` 拒绝（半开，400 本身可入） |
| 迟到容差 lateness_ms | 700 | `watermark - p.Time > 700` 拒绝 |
| 未来容差 future_ms | 100 | `p.Time - now > 100` 拒绝（1800 本身可入，1801 拒绝） |
| 原子性 | 每请求整批成功或整批 409 | `policy.Admit` 先全量校验，任一不过即返回，无点落库 |
| 同时间覆盖 | 同 series 同时间戳，最近提交值覆盖 | PROJECT_SPEC：Repeated timestamps use the most recently committed value |
| rate | 窗口内需 ≥2 点；下降按复位处理；分母=末点-首点真实耗时 | `internal/window/rate.go` |
| labels | 两台 labels 完全相同 → **同一个 series** | `model.SeriesID` 对 labels 做哈希 |

**真实时间换算**（δ = 本地时间 − 真实时间，单位 ms）：

- a：δ_a = +400（已确认）→ 真实时间 = 本地 − 400
  - 本地 1000 / 值 2 → **真实 600 / 2**
  - 本地 2000 / 值 4 → **真实 1600 / 4**
- b：δ_b ∈ [-300, 300]（未确认，两点共用同一偏差）
  - b1：本地 500 / 值 3 → 真实时间 ∈ **[200, 800]**
  - b2：本地 1500 / 值 5 → 真实时间 ∈ **[1200, 1800]**

**来源保留**：因 labels 必须完全相同，入库后 a、b 落在同一 series，引擎内无法用 label 区分来源。
来源信息保存在 `batches/provenance.json`（source、source_local_time、偏差推导式）。
注意 Ridgeline 写接口启用 `DisallowUnknownFields`（`wire/json.go`），请求体出现 `_meta`/`_provenance`
等额外字段会被 400 拒绝，因此**可提交文件只含 now/points/labels/time/value**，来源信息单独存放；
不要为区分来源而改动 labels（否则会产生第二个 series，破坏同一计数器的 rate 语义）。
该约束已由 `replay/verify_artifacts.py` 实测：01 号文件原样 POST 返回 200，03 号模板原样 POST 返回 400。

## 2. 三层可发布范围（明确区分）

### 第一层：现在即可确认并提交（无任何猜测）

- 文件：`batches/01-submit-source-a.json`（纯净请求体，可直接 POST；已实测 200 接受）
- 来源映射：`batches/provenance.json`
- 内容：`(time=600, value=2)`、`(time=1600, value=4)`，now=1700
- 实测回执：`accepted=2, new_series=1, watermark=1600`
- 这两个点在所有 16 个复放场景中只要单独提交就 100% 入库。
- 看板可展示这两个**原始计数点**；据此算出的 rate=2/s（增量 2 ÷ 真实耗时 1.0 s）只能标
  **"临时，待 b 对账"**，因为 b 若有落在同窗口的点会改变可见序列与 rate。

### 第二层：拿到 b 的校时记录后能补的范围

- 模板：`batches/03-backfill-template-source-b.json`（两个 `time` 是非数字占位符，
  原样提交必然 400，禁止预填猜测值）；确认偏差后只替换这两个时间字段。
- 记录到达后，用确认的 δ_b 计算 `time = 本地 − δ_b`，并按**提交 a 之后 watermark=1600** 的口径逐条核对：

| b 点 | 可行真实时间 | 补入条件（watermark=1600, floor=400, now=1700） | 可补 δ_b 区间 |
| --- | --- | --- | --- |
| b2（值5） | [1200,1800] | 迟到线 1600−t ≤ 700 恒成立；未来线 t ≤ 1800 | **δ_b ∈ [-100, 300] 可补**；δ_b ∈ [-300,-101] 因 t>1800 被未来容差拒绝 |
| b1（值3） | [200,800] | 迟到线要求 t ≥ 900，而 t 最大仅 800 | **a 已提交后 δ_b ∈ [-300,300] 全程不可补**（δ>100 时还同时撞 floor=400） |

> 反事实备注：b1 并非天然不可入库。在 a 尚未提交、watermark 仍为 1000 时，迟到线是 300；
> 若 δ_b 已知且落在 [-100,100]，b1 的真实时间 ∈ [400,600]，本可与 a 同批准入。
> 先发 a 使该选项关闭——这是本次决定的显式代价。等待期间若 retention 被推进使 floor 抬高，
> b1 也可能独立死于保留边界，接班时应先 `GET /spaces/device01` 核对当前 floor。

- 补报操作要点：
  - **不要把 b1、b2 放进同一个请求**——b1 必被拒，会把可入库的 b2 一起 409 掉（实测确认）。
  - 先 `GET /spaces/device01` 查看当前 floor/watermark；若期间又推进过 retention，按新 floor 复核。
  - b2 用**单点请求**提交；若 δ_b 落在 [-300,-101]，b2 也无法在 now=1700 下入库，
    需评估是否在更晚的 now 下仍受 future 约束（future 是相对 now 的，now 推进后可解除，
    但要重新走一次准入核对，不要直接重放旧请求）。

### 第三层：交班时仍无校时记录 → 不能作为正式 rate 发布的区间

- b 的两个点（真实时间区间 b1∈[200,800]、b2∈[1200,1800]）在 δ_b 未确认前：
  - 不产生任何可提交请求（`batches/02-hold-source-b-raw.json` 仅保存原始来源与可行区间，
    结构上就不是写请求体，`submittable:false`）。
  - 凡覆盖这些真实时间区间的 rate/count 看板单元，一律**不得标为正式**。
  - 具体地，[0,2000) 窗口的合并计数器 rate 在无校时记录前只能挂"临时（仅 a 来源）"，
    因为 b 一旦补入会改变窗口内点数、首末时间与增量（见第 4 节实测，rate 在 2～8.18 之间摆动）。
- 若到交班仍无记录：正式 rate **空缺**，只保留第一层的两个原始点与临时 rate 标识，
  并在交接记录中写明待补条件（δ_b 确认 + 第二层表格的逐条准入核对）。

## 3. 两种提交安排（用代表性可行偏差复放）

复放脚本 `replay/replay.py` 对每个场景起一个**独立临时库 + 独立 Ridgeline 进程**，
先种入 watermark=1000 的无关 series、推进 retention 得到 floor=400，再执行方案，
并用一份独立的 Python 期望模型（同样实现三条准入规则 + watermark 演进 + rate 公式）交叉核对。
16 个场景全部 `match=true`。原始数据见 `replay/result.json`。

代表性偏差：δ_b ∈ {-300, -101, -100, 0, +100, +101, +300}（覆盖 floor / future 的边界两侧）。

### 方案 A：只提交确认的 a（b 暂缓，记录到后再补）

b 的两点请求在 a 提交后**对所有 δ 都 409**（b1 永远越界，原子性拖垮 b2）：

| δ_b | b 两点请求结果 | 可见点（真实时间,值） | 可见数 | rate[0,2000) |
| --- | --- | --- | --- | --- |
| -300～300（任意） | 409（b1 迟到；δ>100 时 b1 撞 floor） | [600,2],[1600,4] | 2 | 2.0（临时） |

**拆分单点重试**（把 b2 从必失败的请求里摘出来单独提）实测可挽回 b2：

| δ_b | b1 单点 | b2 单点 | 可见点 | 可见数 | rate |
| --- | --- | --- | --- | --- | --- |
| +300 | 409 floor（t=200） | 接受（t=1200） | [600,2],[1200,5],[1600,4] | 3 | **7.0** |
| -300 | 409 迟到（t=800） | 接受（t=1800） | [600,2],[1600,4],[1800,5] | 3 | **2.5** |

注意 δ=-300 时两点请求里 b2 因 t=1800 本可入库，却被 b1 的 409 连坐；拆分后才救回——
这正是"整批失败如何改变可见计数"的直接证据。

### 方案 B：把 a 与猜测的 b 时间戳捆成一个原子请求（仅作反面对照，禁止用于生产）

在 watermark 仍为 1000 时评估（尚未提交 a，迟到线=300）。
注意：这些结果同时是第 2 节反事实备注的实测证据——δ=0、+100 时 b1（t=500、400）
确实能在 wm=1000 的同批请求中准入，而先发 a 后该选项消失。

| δ_b | 结果 | 可见点（真实时间,值） | 可见数 | rate | 说明 |
| --- | --- | --- | --- | --- | --- |
| -300 | 接受 | [600,2],[800,3],[1600,4],[1800,5] | 4 | 2.5 | |
| -101 | 接受 | [600,2],[601,3],[1600,4],[1601,5] | 4 | 2.997 | 顺序几乎交错 |
| -100 | 接受 | **[600,3],[1600,5]** | **2** | 2.0 | **同时间覆盖**：b 与 a 时间戳相同，b 后写覆盖 a 的值 2→3、4→5 |
| 0 | 接受 | [500,3],[600,2],[1500,5],[1600,4] | 4 | **8.18** | 顺序变化：b 点插在 a 点之前，下降 3→2 触发计数器复位 |
| +100 | 接受 | [400,3],[600,2],[1400,5],[1600,4] | 4 | 7.5 | b1 恰在 floor=400，半开边界允许 |
| +101 | **409 整批失败** | 无（a 也丢） | 0 | 无 | b1 t=399 < floor 400 |
| +300 | **409 整批失败** | 无（a 也丢） | 0 | 无 | b1 t=200 < floor 400 |

三类机制对可见计数与 rate 的影响，实测如下：

1. **整批失败**：δ=101、300 时一个越界点让 4 个点全部不可见（计数 4→0，无 rate）。
2. **同时间覆盖**：δ=-100 时两组点时间戳完全重合，b 覆盖 a，计数 4→2；rate 数值碰巧仍为 2.0，
   但底层值已不是 a 的原始值，看板若不看来源会误判。
3. **顺序变化**：δ=0 时 b 的点排到 a 前面，值 3→2 构成下降，按计数器复位语义
   （`rate.go` 中 delta<0 时取当前值），rate 抬到 8.18；说明在偏差未确认时发布的 rate 不具稳定性。

## 4. 复放复现步骤

```sh
# 1. 构建（本机 Go 1.25；仓库已 pin 依赖）
go build -o /tmp/ridgeline-work/bin/ridgeline ./cmd/ridgeline

# 2. 复放全部 16 个场景（每个场景独立临时库，进程结束即清理）
python3 -I handoff/replay/replay.py \
  --binary /tmp/ridgeline-work/bin/ridgeline \
  --out handoff/replay/result.json
# 期望输出：{"scenarios": 16, "all_match": true}

# 3. 交付物自检：01 号文件原样可提交，03 号模板原样被拒
python3 -I handoff/replay/verify_artifacts.py \
  --binary /tmp/ridgeline-work/bin/ridgeline
# 期望末行：ARTIFACT CHECKS PASSED
```

`result.json` 内含每个场景的完整 HTTP 请求/响应轨迹（含 409 的 code/detail）、
watermark 演进、实际查询结果与独立期望模型对照。
