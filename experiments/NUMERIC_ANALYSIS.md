# float64 归约数值分析：sum / avg / 分组 rate

本文档说明 Ridgeline 当前 float64 顺序累加结果的可信范围、实际运算顺序与
溢出处理，给出能够区分**舍入漂移 / 业务定义差异 / 数据可见性差异**三类现象
的实验设计，比较可行的数值策略，并给出误差承诺的数据范围、可重复性代价与
是否改变归约状态的建议。

约束（来自需求）：保留 float64 存储与现有 HTTP API，本阶段不改生产实现。
本文与 `experiments/` 下的实验程序均不被生产代码导入，也未修改任何
`internal/`、`cmd/` 文件（仅新增 `experiments/` 目录）。

## 1. 实际运算顺序（先把“结果是怎么算出来的”讲清楚）

### 1.1 sum / avg / count / min / max：`internal/window/reduce.go`

- 入参顺序由查询层决定，而不是任意的：
  - `engine/scan.go` 先按 series ID 升序选序列（`select.Pick`，
    `internal/select/match.go:69`），每个序列内部再按时间升序排序
    （`scan.go:109`）。
  - `window.Aggregate` 按该顺序遍历序列、再遍历点
    （`reduce.go:31-56`），把同一个 `(group, bucket)` 的所有点累加到
    **一个** float64 寄存器：`a.sum += p.Value`（`reduce.go:47`）。
  - 因此 sum 的结合顺序是确定性的“序列 ID 升序 → 时间升序”的左结合顺序
    求和，而不是并行/树形求和。Go 的 map 迭代顺序是随机的，但 map 只用于
    定位 accumulator，不决定点的加法顺序；输出在返回前统一排序
    （`reduce.go:81` → `bucket.go:45`），所以 map 的随机性不影响数值。
- avg 复用同一个 sum 寄存器，最后只做一次除法：
  `a.sum / float64(count)`（`reduce.go:66`）。它对**观测点**加权，不对
  序列加权（见 PROJECT_SPEC.md “An average weights observations, not
  series”）。
- min/max 是单调选择运算，无数值累加误差；count 是整数计数，转 float64 后
  在扫描上限 2,000,000 内远小于 2^53，精确。
- first/last 是选值，不做算术。
- 没有任何 FMA/融合乘加（已全仓检索 `FMA|fma` 无匹配），每条 `+=`、`-`、
  `/` 都是一次 IEEE-754 binary64 就近舍入（round-to-nearest-even）操作。

### 1.2 分组 rate：`internal/window/rate.go`

每个序列、每个窗口独立计算，再跨序列相加：

1. 先把该序列窗口内的点按时间收集（查询层已保证时间升序）。
2. 任何点 `Value < 0` 直接返回 `invalid`（`rate.go:16-18`），即 rate 只接受
   非负计数器。
3. 逐点做差 `delta := v[i] - v[i-1]`；若 `delta < 0`（计数器下降），按
   “复位为零”语义把 delta 替换为当前值 `v[i]`（`rate.go:28-31`）。
4. 用一个 float64 寄存器顺序累加这些 delta（`rate.go:32`）。
5. 分母 `elapsed` 是**末点与首点时间戳之差**（毫秒）除以 1000
   （`rate.go:34`），不是窗口宽度，也不做任何外推/插值。
6. `increase / elapsed` 得到该序列该窗口的 rate（`rate.go:35`）。
7. 同一 `(group, bucket)` 单元格内，再把各序列的 rate 用一个 float64
   寄存器顺序相加（`rate.go:42`），顺序同样是 series ID 升序。
   点数少于 2 的窗口被跳过（`rate.go:23-25`），因此 elapsed 恒为正，不会
   出现除零。
- 时间戳是 [-2^52, 2^52] 的整数毫秒，两时间戳之差是精确整数，转 float64
  在该范围内精确；`/1000` 引入至多一次舍入。

### 1.3 溢出与非有限值处理（fail-closed，而不是静默饱和）

- 写入侧：`ValidateObservation` 拒绝 NaN/Inf
  （`internal/model/validate.go:49`），所以存储里不可能出现非有限点；
  ±Inf 只能在算术中间产生。
- 归约侧：每个单元格产出后检查 `math.IsInf || math.IsNaN`，命中即返回
  `capacity`（HTTP 422，`reduce.go:76-78`、`rate.go:44-46`）。
- binary64 的 ±Inf 是**粘性**的：一旦某次加法溢出为 +Inf，后续有限数的
  加减无法把它拉回有限值；`+Inf + (-Inf) = NaN`。实验
  （`overflow_cases`）证实：
  - `{MaxFloat64, MaxFloat64, -MaxFloat64}` 数学上有限（=MaxFloat64），但
    顺序求和先溢出成 +Inf，最终非有限 → 422。同一多重集换一个结合顺序
    （`{-MaxFloat64, +MaxFloat64, +MaxFloat64}`）就能得到有限的 MaxFloat64。
    这说明溢出边界对**结合顺序敏感**，当前实现偏保守（宁可拒绝）。
  - 真正发散（两个 MaxFloat64 相加）任何策略都无法给出有限答案，422 是
    唯一安全行为。
- 注意检查在“最终值”上。中间过程若产生又消除了 Inf（例如
  +Inf 后接 -Inf 会变 NaN，仍是 NaN，会被拦），不存在“中间 Inf 被悄悄
  吞掉后返回一个看似有限值”的路径——因为粘性保证最终必然非有限。

## 2. 实验设计：如何区分三类现象

三类现象的根因不同，必须用不同的对照实验隔离。所有实验都是确定性的
（LCG 固定种子、无全局随机源），输出 JSON 报告，重复运行数值位级一致。

| 现象类别 | 判据（控制变量） | 对应实验 |
| --- | --- | --- |
| 舍入漂移 | **可见数据完全相同**，仅把引擎输出与对同一批点的 big.Float(128bit) 精确参考值比较 | 微基准 `numerics_report.json`；端到端 F1/F4b |
| 业务定义差异 | 可见数据相同，但函数语义不同（观测加权 vs 序列加权；复位规则 vs 朴素差商；非负约束） | 端到端 F2/F3/F4 |
| 数据可见性差异 | 查询语句相同，改变哪些点可见（删除墓碑、保留期地板、同时间戳纠正、密封/压缩） | 端到端 F5–F9 |
| 物理布局可重复性 | 可见点集合不变，只改存储形态（head→gzip block→compaction） | 端到端 F5/F8；`roundtrip` |

### 2.1 舍入漂移（同一批可见数据，换“求值精度”）

- 微基准 `experiments/numerics`（`lib/strategies.go`）对同一输入并行运行：
  顺序求和（与生产逐位一致，已交叉验证，见下）、两两树形、Kahan、
  Neumaier、排序后顺序、big.Float 精确求和后一次性舍入。
- 端到端 `experiments/numerics/e2e` 驱动**真实引擎**（真实 bbolt、真实
  `window.Aggregate/Rates`），再用 `/range` 取回引擎实际可见的点，用
  big.Float 独立重算参考值，比较单元格与参考值。这样参考值与引擎用的是
  同一批可见行，杜绝把“少了点”误判成“算错了”。
- 可信度校验：微基准镜像的顺序求和与真实引擎在 1000×0.1 上的输出
  `Float64bits` 完全相同（99.9999999999986），证明微基准的误差数字可以
  代表生产路径。

### 2.2 业务定义差异（同一批数据，换“定义”）

- F2：构造三个观测点数不等的序列（1000/1000/10），比较引擎 avg
  （观测加权，sum/2010）与“各序列均值再等权平均”。二者相差 56% 相对量，
  这是定义差异而非浮点误差（误差量级在 1e-14）。
- F3：含一次下降的计数器，比较生产 rate（复位规则，increase=220/3s
  ≈73.33）与朴素首尾差商（(120−1000)/3 ≈ −293.33）。后者对计数器无意义。
- F4：写入负值后调 rate，确认返回 `invalid: counter rate requires
  nonnegative values`，这是契约约束，不是数值问题。

### 2.3 数据可见性差异（同一查询，改变“能看到哪些点”）

- F6 删除：对 zone=a 建墓碑删掉 500 个点，sum 单元格恰好下降约 500×0.1
  （观测到 -49.99999999999815，含 0.1 不可精确表示的浮点因素）。
- F7 纠正：同一时间戳 t=600 重写为 5.0，最高 sequence 生效，单元格只变化
  一次（≈4.9）。
- F9 保留期：在一个 RetentionMS=1000 的独立命名空间推进 floor 越过所有点，
  单元格直接消失（1→0）。保留期是单调且不可逆的物理移除，与删除不同。
- 对照 F5/F8：密封（head→gzip block）和压缩（合并 block、套用墓碑）前后，
  同一聚合查询的所有单元格**逐位相同**。这把“物理布局变化”与“可见数据
  变化”干净地分开：布局不变结果，可见性才变结果。

### 2.4 持久化可重复性

`experiments/numerics/roundtrip` 验证两条持久化边界（JSON 与
gzip+JSON+SHA-256 的 block 格式 `chunk.Encode/Decode`）对 13 个跨量级
探针（含次正规数、±0、2^53 边界、1e308）均**逐位还原**。Go `encoding/json`
用最短往返表示编码 float64，配合二进制 block，存储层不引入任何额外舍入。

## 3. 实测结果与误差量级

完整机器可读数据见 `experiments/numerics/out/`：
`numerics_report.json`、`e2e_report.json`、`sweep_report.json`、
`roundtrip_report.json`。环境：go1.25.0 linux/arm64（CGO_ENABLED=0）。

### 3.1 sum：良性数据下误差随 n 线性增长，且远低于理论上界

0.1 重复增量（0.1 在 binary64 不可精确表示），顺序求和实测：

| n | 顺序求和相对误差 | 顺序求和 ULP | 两两树形相对误差 | Neumaier | 理论上界 (n-1)ε |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 1.1e-16 | 0 | 1.1e-16 | 0 | 1.0e-15 |
| 1,000 | 1.4e-14 | 99 | 9.9e-16 | 0 | 1.1e-13 |
| 100,000 | 1.9e-12 | 10,362 | 3.6e-16 | 0 | 1.1e-11 |
| 2,000,000 | 3.6e-14 | 245,797 | 8.7e-16 | 0 | 2.2e-10 |

- 实测相对误差约为理论上界的 1/6；n=2e6 时仍是 3.6e-14（约 13 位有效
  数字可信）。
- 两两树形把误差压到 ~4ε 且与 n 几乎无关；Neumaier 在所有良性场景误差为
  0（相对精确参考值舍入后相同）。
- 整数单位增量（全为精确 1.0）在 2e6 规模下顺序求和**精确为 0 误差**，
  因为结果未超过 2^53 的精确整数范围。典型有界正计数器
  （`realistic_counters`，500k 个 100..1000 的整数）所有策略都是 0 误差。

### 3.2 抵消：相对误差承诺在精确和接近 0 时失效，且原因在存储而非求和

- `cancellation_pairs`（±1e15 成对，精确和为 0）：所有策略都正确得到 0，
  但“相对误差”无定义（分母为 0）——这类数据只能承诺**绝对误差**。
- `catastrophic_cancellation_residual`（每对 1e15+0.1 与 -1e15，实数残差
  0.1/对）：由于 0.1 在 1e15 量级低于半个 ULP，`1e15+0.1` 在**存储取值
  阶段**就被舍入成 1e15，每对在 binary64 里实际贡献 0。big.Float 对“已
  存成 float64 的输入”求和同样得到 0。这证明信息在输入表示时已丢失，
  换任何求和算法（Kahan/Neumaier/树形/大浮点）都救不回来——这是数据范围
  问题，不是归约顺序问题。
- `large_plus_tiny`（1e16 锚点 + 1e6 个 1.0）：顺序求和丢掉全部单位增量
  （相对误差 1e-10，50 万 ULP）；同数据反向顺序（先小后大）误差为 0，
  暴露顺序敏感性；Neumaier/排序求和/精确求和都为 0。扫描显示当运行和
  ≥ 2^53（≈9.007e15）时 `sum+1.0 == sum`，这是硬表示天花板。

### 3.3 avg

avg 继承 sum 的误差再加一次除法舍入。端到端 1000 点：
- zone a：引擎 0.09999999999999859 vs 精确 0.1，相对 1.4e-14（102 ULP）。
- 除法本身至多 1 ULP，avg 的误差主体仍在 sum 阶段；用 Neumaier 的 sum
  再除，误差降到 1 ULP 以内。

### 3.4 分组 rate

| 场景 | 序列×点 | 生产相对误差 | ULP | 备注 |
| --- | --- | --- | ---: | --- |
| 0.1/s 小增量 | 200×10,000 | 1.8e-15 | 10 | 约 2e6 次 delta 累加 |
| 整数单位 | 200×10,000 | 0 | 0 | 增量精确 |
| 含周期复位（1e9 基数） | 100×20,000 | 0 | 0 | 复位规则不引入误差 |
| 1e16 吸附计数器 | 1×50,000 | 0 | 0 | 单位 delta 在减法里就是 0，表示天花板 |
| 1e12 大增量与复位交替 | 1×100,000 | 8.2e-13 | 6,716 | 大运行和吸收小的复位 delta |
| 端到端分组 rate（3×2000，含复位） | — | 4.4e-14 | 242 | 真实引擎 vs big.Float |

rate 的误差结构与 sum 同源（delta 顺序累加 + 跨序列 rate 顺序累加），
但 delta 数量受每窗口点数限制，典型误差比同规模纯 sum 更小。
“吸附计数器”再次说明：当计数器值越过 2^53，单位级增长在 `v[i]-v[i-1]`
里就已经是 0，任何归约状态都无法恢复——必须靠采集侧避免在该量级用
float64 记小增量（例如改用整数计数器或分段基数）。

### 3.5 排序后求和是一个反例，不要采用

`sorted_then_sequential` 在良性数据上尚可，但在 18 个数量级的带符号混合
数据上误差达 1.5e5（相对）甚至在 ±1e308 链上直接溢出成 Inf：按带符号值
排序会让同号超大值连续相加触发中间溢出，而原始交错顺序反而精确抵消。
因此“先排序再求和”在本工作负载下既慢（额外 O(n log n)）又更危险，
不予推荐。

## 4. 数值策略比较

| 策略 | 相对误差（良性，n=2e6） | 单趟耗时（2e6 点，参考） | 额外内存/点 | 与现有流式模型兼容性 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 顺序求和（现状） | 3.6e-14（实测），上界 2.2e-10 | ~3.4 ms（基准 1×） | 0 | 完全兼容（单寄存器） | 保留 |
| 两两树形 | 8.7e-16（~4ε，与 n 无关） | ~1.6 ms（更快，缓存友好） | O(log n) 栈/分块缓冲 | 需缓冲窗口内全部值，破坏单遍流式 | 精度好但改造面大 |
| Kahan | 0（多数场景） | ~12 ms（~3.6×） | +16B（补偿项） | 可单遍流式 | 经典但运行和变小时偏弱 |
| **Neumaier（改进 Kahan）** | **0（全部良性场景）** | ~3.5 ms（**≈1.03×，几乎免费**） | +16B（补偿项） | **可单遍流式，仅多一个寄存器** | 若未来要提精度，首选 |
| 排序后顺序 | 反例：1.5e5 误差 / 溢出 | ~16–260 ms | +8B 拷贝 | 需全量缓冲+排序 | 否决 |
| big.Float(128) 精确后舍入 | 0 | ~165 ms（**~50×**） | 大量堆分配 | 需全量值，无法流式 | 仅适合离线审计，不适合热路径 |

补充：
- Neumaier 与 Kahan 都**不能**修复 3.2 的输入侧抵消（信息已丢）、3.4 的
  2^53 吸附，也不能让真正发散的和变有限；它们只消除“结合顺序导致的
  舍入漂移”。
- big.Float 的价值是作为**测试/审计的参考实现**（本实验正是如此使用），
  50× 的 CPU 代价与不可流式使其不适合查询热路径。
- 所有策略产出仍走同一个 `IsInf/IsNaN` 422 关卡，失败封闭语义不变。

## 5. 误差承诺：适用数据范围、可重复性代价

### 5.1 可承诺的误差边界（在以下数据范围内）

设单元格内参与一次归约的点数为 n（受 `MaxScan ≤ 2,000,000` 约束），
binary64 机器 ε = 2^-53 ≈ 1.11e-16。

1. **良性求和（sum）**：当条件数
   `κ = Σ|xᵢ| / |Σxᵢ|` 有界且精确和不接近 0 时，标准先验上界
   `|err| / |S| ≤ (n-1)ε / (1-(n-1)ε)`；在 n=2e6 即 **2.22e-10**。实测
   仅为该上界的约 1/6（3.58e-11），可保守承诺“良性数据下相对误差
   ≤ 2.3e-10（约 ≥9 位有效十进制）”，典型数据实测在 1e-13 量级。
2. **avg**：在 sum 承诺上再加一次除法舍入（≤1 ULP），同一数据范围内
   可承诺同样量级的相对边界；观测点加权，count 精确。
3. **rate**：每窗口 delta 数 ≤ 可见点数，分母（毫秒时间戳差/1000）在
   [-2^52,2^52] 内精确转换；可对 increase 套用与 sum 相同的
   `(m-1)ε` 良性边界（m=delta 数），再加一次除法舍入。实测 2e6 delta
   相对误差 1.8e-15。
4. **绝对误差兜底**：当精确和为 0 或 κ 很大（强抵消）时，**不承诺相对
   误差**；改承诺绝对误差，其量级约为 `(n-1)ε·Σ|xᵢ|`，并在文档/API
   说明中明确“抵消场景相对误差无定义”。
5. **表示天花板（硬约束，非归约缺陷）**：
   - 输入值与运行和在 |x| < 2^53 ≈ 9.007e15 以内时，整数级增量可被
     表示与累加；越过 2^53 后 `x+1 == x`，单位级增量不可恢复。
   - 单值受 binary64 有限范围约束（< 1.8e308）；算术中间溢出一律 422，
     不返回非有限 JSON。
   - 时间戳合法域 [-2^52, 2^52] 毫秒；rate 要求窗口内 ≥2 个非负点。

### 5.2 可重复性（确定性）及其代价

- **数值确定性是免费的**：同一二进制 + 同一可见数据集，sum/avg/rate
  输出逐位一致。依据：
  - 点加法顺序由 series ID 升序 + 时间升序固定，与 Go map 随机迭代无关；
  - 无 FMA，每条运算一次就近舍入；Go 的 float64 在 amd64/arm64 上映射
    硬件 binary64 运算，不使用扩展精度；
  - JSON 与 gzip block 两条持久化路径逐位保留 float64（roundtrip 实验）；
  - 密封/压缩只改物理布局，端到端 F5/F8 证明单元格逐位不变。
- 重复运行实验，除墙钟时间戳和 `nanos_per_op` 外，所有数值字段完全一致
  （已两次运行 diff 验证）。
- **代价仅在“精确参考值”一侧**：用 big.Float(128) 做审计参考，2e6 点
  单趟约 165 ms（约为生产求和的 50 倍）且需要全部值在内存。生产查询
  不付这个代价；只有离线对账/测试才需要。
- 跨架构注意：承诺依赖 IEEE-754 binary64 与无 FMA 收缩。当前代码满足；
  若未来引入编译器 FMA 收缩或换用非标准浮点硬件，需要重新跑
  `experiments/run_experiments.sh` 校准。

## 6. 是否改变归约状态：建议

**建议：本阶段保持现状（顺序 float64 累加 + 末尾 IsInf/IsNaN 422 关卡），
不改生产实现、不改存储与 API。** 理由：

1. 现状在良性数据上的实测误差（1e-13 量级，最坏上界 2.2e-10）远优于
   float64 存储本身的表示极限，典型有界运营计数器甚至 0 误差；归约顺序
   不是当前主要误差来源。
2. 真正大的偏差都来自**表示/数据范围**（2^53 吸附、输入侧抵消）与
   **可见性/定义**，换归约算法（含 big.Float）都无法解决，改了会给人
   一种“已经修好”的错觉。
3. 当前没有持久化的部分归约状态：rollup 物化的是最终单元格
   （`engine/rollup.go`），reducer 是查询期单遍流式。因此现在改 reducer
   不涉及磁盘状态迁移，反而说明“归约状态”目前没有沉没成本，未来若要改
   可以平滑进行——但不构成现在就改的理由。

**若未来出现更严格误差 SLA（例如要求任意顺序下 ≤ 几 ULP），按优先级：**

1. 首选把 `reduce.go`/`rate.go` 的单寄存器累加换成 **Neumaier 补偿求和**：
   仅多一个 float64 补偿寄存器，仍可单遍流式，实测耗时几乎不变（≈1.03×），
   良性数据误差降到 0，且不需要改存储格式或 API（输出仍是 float64）。
   建议 behind 一个查询版本/特性开关，配合本实验套件做回归。
2. 两两树形可作为对吞吐敏感场景的备选（实测更快、误差 ~4ε），但需要
   缓冲窗口内全部值，破坏流式、改造面更大，次选。
3. 不要采用“先排序再求和”（有溢出/超大误差反例）。
4. big.Float 仅保留为测试与离线审计的参考实现，不进热路径。
5. 无论选哪种，都保留末尾 `IsInf/IsNaN → 422` 的 fail-closed 检查；并在
   文档中明确抵消场景只承诺绝对误差、|x|≥2^53 的小增量不可恢复。
6. 配套治理（比改 reducer 更能解决真实痛点）：在采集/写入侧对接近 2^53
   的计数器给出指引（整数计数器或分段基数），在 API 文档公布第 5 节的
   误差承诺数据范围，让调用方能区分“浮点漂移”与“数据被删/被纠正/被
   保留期移除”。

## 7. 复现方式

```sh
# 需要 Go 1.25+；脚本内置 CGO_ENABLED=0，无需 C 工具链
bash experiments/run_experiments.sh
```

产出（`experiments/numerics/out/`）：
- `numerics_report.json`：sum/avg 策略对比、顺序探针、rate 用例、溢出用例；
- `e2e_report.json`：真实引擎上舍入/业务定义/可见性/可重复性/溢出 14 项发现；
- `sweep_report.json`：误差随 n 增长曲线与 2^53 吸附阈值；
- `roundtrip_report.json`：JSON 与 block 持久化逐位还原结论。

生产代码未改动；`go build ./...`、`go vet ./...` 与
`python3 examples/walkthrough.py --workflow all`（31 个操作）均通过。
