# Ridgeline 故障演练与恢复运行手册（值班用）

本手册面向值班人员，回答四个问题：服务怎么交付运行、两类“客户端没收到回执”
的事故怎么区分、强制终止与恢复怎么演练并保留独立证据、什么时候可以恢复采集。

## 1. 交付形态与运行配置

交付物：

| 文件 | 作用 |
| --- | --- |
| `deploy/Dockerfile` | 多阶段构建，产出静态二进制；运行时为非 root 用户 `ridgeline`（uid 10001） |
| `deploy/docker-compose.yml` | 正式运行配置：非 root、仅回环开放、命名持久卷、只读根文件系统、drop all caps |
| `deploy/docker-compose.drill.yml` | 演练覆盖：关闭自动重启，保证 SIGKILL 后容器保持死亡状态以便取证 |
| `drill/fault_proxy.py` | 确定性故障注入代理（标准库 Python，`-I` 隔离模式运行） |
| `drill/replay.py` | 可重放演练编排：两条边界、强制终止、独立取证、整批核对、判定恢复 |

安全与持久化要点（`docker-compose.yml`）：

- `user: "10001:10001"`，镜像内也通过 `adduser` 固定同名非特权用户；进程不以 root 运行。
- 端口发布为 `127.0.0.1:8399:8399`，宿主机回环地址独占绑定，局域网与其他主机不可达。
  容器内进程监听 `0.0.0.0:8399` 仅在容器网络命名空间内有效，对外暴露面由发布规则决定。
- 命名卷 `ridgeline-data` 挂载到 `/var/lib/ridgeline`，是唯一可写路径（根文件系统
  `read_only: true`，`/tmp` 为 noexec tmpfs）。**重建容器复用同一个卷**，
  `docker compose up -d --force-recreate` 不会丢数据；`down`（不带 `-v`）同样保留卷。
- `cap_drop: [ALL]`、`no-new-privileges`、`pids_limit`、`mem_limit` 限制爆炸半径。
- 正式配置 `restart: unless-stopped`；演练时叠加 drill 覆盖改为 `restart: "no"`，
  否则守护进程会在取证前自动拉起容器，破坏现场。

启动与重建：

```sh
# 构建并启动（首次）
docker compose -f deploy/docker-compose.yml up -d --build
curl -s http://127.0.0.1:8399/ridge/v1/health

# 用同一个持久卷重建容器（验证卷复用）
docker compose -f deploy/docker-compose.yml up -d --force-recreate
docker volume inspect ridgeline-data          # 卷仍在，数据延续
```

## 2. 两类“没有回执”事故的判定边界

客户端看到的现象完全一样：写请求没有拿到 HTTP 200 回执。但故障落点只有两种，
恢复动作完全相反，**绝不能凭最终数据反推**，必须用独立证据在事故当下定位：

| | 边界 A：请求未送达服务端 | 边界 B：服务端已提交，回执未达客户端 |
| --- | --- | --- |
| 网络事实 | 代理接收了完整请求，但从未向上游打开连接 | 代理已把请求转发给服务端，并读到完整上游响应 |
| 服务端事实 | bbolt 中不存在该批数据，序列不变 | bbolt 已提交，序列递增；响应已在服务端 socket 上 |
| 客户端事实 | 超时/连接失败，无回执 | 响应被代理扣押，客户端同样无回执 |
| 恢复动作 | **整批重发**（重发是安全的，见 §5） | **禁止重发**，只做整批核对确认 |
| 判定证据 | 代理 `fault_block_no_upstream` + 崩溃快照序列未变 | 代理 `upstream_response_received` + `fault_hold_response_withheld` + 崩溃快照序列与被扣押回执中的 sequence 一致 |

关键原则：**序列（sequence）是服务端提交的权威事实**。每条成功变更单调递增，
命名空间的 `last_sequence` 与点上的 `sequence` 都在同一个 bbolt 事务里落盘。
因此“快照里的序列”可以独立回答“服务端当时到底提交了没有”，不需要事后猜测。

## 3. 三条独立证据链（不允许事后反推）

演练对每条边界都强制保留三份在事故当时产生、彼此独立的证据：

1. **客户端台账** `evidence/client-ledger.jsonl`
   记录每批发出发送时间、点数、走的路径（直连/代理）、HTTP 状态、回执原文或
   异常类型（`TimeoutError` / `RemoteDisconnected`）。这是“客户端视角”的原始记录。
2. **代理线路日志** `wire.jsonl`
   每个连接事件一行带毫秒时间戳：请求是否到达、是否打开上游连接、上游是否返回、
   响应是否被扣押。这是“网络视角”的第三方记录，客户端和服务端都无法改写它。
3. **崩溃快照与独立校验** `evidence/<scenario>-crash-snapshot.db`
   SIGKILL 之后、恢复之前，直接复制 bbolt 文件并记录 SHA-256；随后由**另一个
   Ridgeline 进程/容器打开该副本**（校验副本与快照字节一致、路径独立）读取
   `last_sequence`。这是“存储视角”的现场冻结，先取证、后恢复。

报告 `evidence/drill-report.json` 把三条证据链对齐，并给出每条边界的判定结论。
判定逻辑只引用事故当时的记录，不用恢复后的最终数据倒推动机。

## 4. 可重放演练

### 4.1 本地进程后端（无需 Docker，CI/本机均可）

需要先构建静态二进制（演练与镜像使用同一份 Go 源码）：

```sh
CGO_ENABLED=0 go build -o build/ridgeline ./cmd/ridgeline
python3 -I drill/replay.py --backend local --work var/drill
```

### 4.2 Docker Compose 后端（交付形态本身）

```sh
python3 -I drill/replay.py --backend compose --work var/drill-compose
```

compose 后端的每一步对应生产动作：`compose up` 启动、`compose kill`（SIGKILL）
强杀、只读挂载命名卷复制 db 文件、用独立临时卷起校验容器、再次 `compose up`
用同一卷恢复。

### 4.3 演练时序（两条边界各一次强制终止 + 恢复）

```
控制批 ctrl-0001 直连写入并拿到回执（对照，必须在两次崩溃后仍然完整）
  │
边界 A（block 模式）：代理收下 batch-a 但不连上游 → 客户端超时无回执
  ├─ 等待故障触发 → SIGKILL 强杀（returncode -9 / docker State=exited 137）
  ├─ 崩溃后复制 db 快照、记哈希、独立进程打开副本核对序列=控制批序列
  ├─ 用同一卷恢复，健康检查通过（仅健康不等于恢复完成）
  └─ 整批核对：恢复后 batch-a 必须不存在 → 整批重发 → 再核对必须恰好一份完整数据
  │
边界 B（hold 模式）：代理转发 batch-b、读完整上游 200 响应但扣押不发给客户端
  ├─ 客户端超时无回执 → SIGKILL 强杀
  ├─ 快照独立校验：序列 == 被扣押响应里的 sequence（证明已提交）
  ├─ 用同一卷恢复
  └─ 整批核对：batch-b 必须已完整存在；禁止重发
  │
收尾：对照控制批整批核对（必须存活且点数不变）；输出序列全链路
```

### 4.4 通过判据（全部满足才算演练通过）

- 边界 A：客户端无回执；代理日志无任何上游连接；崩溃快照序列未推进；
  恢复后、重发前整批查询为空；整批重发后查询结果与请求逐点一致且仅一份。
- 边界 B：客户端无回执；代理日志同时存在 `upstream_response_received` 与
  `fault_hold_response_withheld`；被扣押回执的 `sequence` 与崩溃快照
  `last_sequence` 相等；恢复后不重发，整批查询逐点一致且仅一份。
- 控制批：两次 SIGKILL 与恢复后，已回执的对照写入逐点保留。
- 卷复用：三次启动的卷/db 身份一致（本地为设备号+inode，compose 为卷名+inode）。
- 证据完整性：校验副本与崩溃快照 SHA-256 相同，且校验发生在独立路径/独立卷。

任何一条不满足，`replay.py` 以非零码退出并在 `drill-report.json` 的
`failures` 中列出原因。

## 5. 重发为什么是安全的（边界 A 的恢复手段）

Ridgeline 的写入语义是“同序列覆盖、以时间戳为点键”：`(命名空间, 标签集, 时间戳)`
唯一确定一个点，重复时间戳取最近提交值。整批重发同一请求不会产生重复点，
只会把相同值再写一遍。因此边界 A 的标准恢复动作就是**按原批次整体重发**，
而不是拆点补发；边界 B 由于服务端已提交，重发虽不产生重复点，但会制造一条
多余的序列、污染审计轨迹，所以禁止重发，只核对。

## 6. 何时可以恢复采集（放行条件）

故障窗口内**先停止新写入**，按顺序完成下列检查后才允许生产者继续采集。
仅健康检查恢复、或仅看到旧值仍存在，都不构成恢复完成：

1. **服务就位**：容器/进程已用同一持久卷重新拉起，`GET /ridge/v1/health`
   返回 `ready`，且卷身份与事故前一致（证明没有挂错空卷）。
2. **现场已冻结**：崩溃快照已复制、哈希已记录、独立校验已完成并归档。
3. **逐批核对所有未回执批次**，对每批给出明确归类：
   - 证据指向边界 A（未提交）→ 整批重发 → 复查逐点一致、仅一份；
   - 证据指向边界 B（已提交）→ 不重发，复查逐点一致、仅一份；
   - 证据不足无法归类的批次，按边界 A 处理（重发幂等），并在台账标注。
4. **对照写入存活检查**：事故前已拿到回执的控制批/最近一批已确认数据，
   整批查询逐点保留，确认持久卷没有回退或损坏。
5. **序列连续性检查**：当前 `last_sequence` 与各回执/快照中的序列对得上，
   不存在序列倒退；之后第一条新写入拿到的回执序列应严格递增。
6. 以上全部记入事故记录（台账、线路日志、快照哈希、核对结果），值班复核签字。

满足 1–6 后恢复采集。若第 3 步仍有批次无法归类，或第 4/5 步发现数据缺失、
序列异常，保持写入停止状态，按 `README.md` 的镜像恢复流程（`/ridge/v1/image`
+ `RIDGE_DB` 还原 + 序列/水位/原始点比对）处置，不得带疑团放行。
