# 补报接入手册：独占流核对、共享流归因与回执可确认性

本手册面向接手同一批补报的两个采集端：一个设备的序列由单一客户端独占写入
（下称**独占流**），另一个设备的同一时间戳可能被别的客户端修正（下称**共享
流**）。手册只使用 Ridgeline 现有 HTTP 接口（`/ridge/v1`），不假设任何新功能。

旧客户端的两个习惯是事故根源：

1. **收到成功回执就把 `accepted` 计入新增量** —— `accepted` 并不等于新增量；
2. **超时就整批重送** —— 在共享流上会盖掉另一客户端刚刚提交的修正。

本手册给出替代流程，并用可重放的 HTTP 例子验证每一步。所有带步骤编号
（A1、B3、C4g、D4……）的引用都对应 `examples/backfill/transcript.json` 里
真实录制的请求/响应；重放方式见附录。

---

## 1. 接口语义基线

以下每条都是现有实现的确切行为，是后续流程的推理基础。

### 1.1 写入与回执

`POST /ridge/v1/spaces/{space}/points`，请求体 `{"now": N, "points": [...]}`。

- **单请求原子**：任一点违反策略或校验，整个请求被拒绝，一个点也不落库。
- 回执：`{"sequence": S, "accepted": A, "new_series": K, "watermark": W}`。
  - `sequence` 是本次提交的全库单调序号；**本批所有点都以这个 sequence 落库**，
    它是这一批的指纹。
  - `accepted` **就是请求里 points 数组的长度**：批内同 `(series, time)` 重复
    出现几次算几次；覆盖已存在的点也照样计数。它不是"新增可见点数"。
  - `watermark` 是命名空间迄今接受过的最大时间戳（用于迟到数据策略）。
- **同时间戳 last-wins**：同一 `(series, time)` 以提交序号更大者为准；同一请求
  内序号相同，**数组中靠后的元素生效**（实录 A4：`accepted=2`，可见点只有
  最后一个值 50）。

### 1.2 读回模型

`POST /ridge/v1/spaces/{space}/range`，请求体
`{"start": S, "end": E, "matchers": [...], "limit": 0}`，区间左闭右开。

- 返回的每个点都带 **`sequence`：当前可见值是哪一次提交写进去的**。该序号在
  `seal`（head 落块）和 `compact`（物理整理）之后保持不变（实录 A5、C3）。
- 顶层 `sequence` 是读时刻的全库序号；`floor` 是当前保留水位（见 1.4）。
- 结果按序列 ID、再按时间戳排序；设了 `limit` 且被截断时 `truncated: true`。
  **对账读不要设 limit**——截断的读回不能作为计数依据。命名空间扫描预算
  超限会返回 422，此时把时间窗切小重查。

### 1.3 删除（tombstone）

`POST /ridge/v1/spaces/{space}/deletions`，请求体同 range（区间 + matchers）。

- 删除不是物理抹除，而是记录一块墓碑：`{id, series, start, end, sequence: D}`，
  隐藏区间内**提交序号 ≤ D** 的样本。
- 删除之后**同一时间戳可以重新写入**：新样本序号 > D，立即恢复可见
  （实录 C2）。
- `GET /ridge/v1/spaces/{space}/deletions` 可列出当前全部墓碑；但 **`compact`
  和 `retention` 会物理结算删除并清空墓碑清单**（实录 C3、C4f）。墓碑是有时效
  的证据，不是永久档案。

### 1.4 保留（retention floor）

`POST /ridge/v1/spaces/{space}/retention`，请求体 `{"now": N}`。

- 把 floor 推进到 `now - retention_ms`（**单调不减**，永不回退），并物理压缩：
  低于 floor 的点被真正丢弃，墓碑清单同时清空。
- floor 不可逆：`time < floor` 的点**永远读不到，也永远写不进**——写入会被
  409 拒绝：`{"code":"conflict","detail":"point precedes retention floor"}`
  （实录 C4g）。
- 任何时刻都可以通过 `GET /ridge/v1/spaces/{space}` 的 `floor` 字段（或任意
  range 响应的 `floor`）确认当前水位。

### 1.5 错误分类与"超时"的含义

| 状态码 | code | 含义 | 是否落库 |
| --- | --- | --- | --- |
| 200 | — | 整批原子提交 | 全部落库 |
| 400 | `invalid` | 请求体/标签/数值非法（如 NaN、坏正则） | 未落库 |
| 404 | `missing` | 命名空间不存在 | 未落库 |
| 409 | `conflict` | 状态冲突：只读、`point precedes retention floor`、`point exceeds future skew policy`、`point exceeds out-of-order time policy` | 未落库 |
| 422 | `capacity` | 容量拒绝：点数超 `max_write`、序列数超 `max_series`、扫描超 `max_scan` | 未落库 |
| 超时/断连/5xx | — | **结果未知**：可能已提交但响应丢失，也可能未提交 | 未知 |

"超时"不是一个结果，而是**没有结果**。处理未知结果的唯一办法是读回核对
（第 3、4 节），而不是假设失败后整批重送。

### 1.6 命名空间自检

`GET /ridge/v1/spaces/{space}` 返回 `read_only`、`floor`、`watermark`、
`last_sequence` 和全部策略限额。补报前和核对前都应先读它：

- `read_only: true` → 写入/删除/保留都会被 409 拒绝，等待运维解除；
- `floor` → 批次中 `time < floor` 的点已终态不可补（见第 5 节）；
- `last_sequence` → 命名空间内任何变更（写/删/保留/整理）都会推进它，
  是最便宜的"期间是否有变化"探针。

## 2. 发送侧纪律（两种流共同遵守）

1. **按流分批**：同一批补报先按设备标签拆成独占流请求和共享流请求，绝不混
   在一个请求里。整批重送的语义对两种流完全不同（第 3、4 节）。
2. **批内去重**：同一 `(series, time)` 在批内只保留最后值。去重后
   `accepted` 才等于"批内不同 `(series, time)` 数"，回执才可解读（但它仍然
   不是新增量，见第 3 节）。
3. **每批一个新鲜的 `now`**：未来偏移策略按 `time - now > future_ms` 判定，
   复用旧 `now` 会让整批被 409 拒绝。
4. **控制批量**：点数 ≤ `max_write`，批内新序列数不顶爆 `max_series`；422
   时把批拆小重发（未落库，安全）。
5. **本地尝试日志**：每发一批，记录 `{batch_id, points, 请求时刻}`；拿到回执
   后补上 `{sequence}`。超时批次**没有** `sequence`——这正是后面"无法归因"
   的来源。日志是删除/保留推进之后唯一剩下的证据（第 5 节），必须持久化。

## 3. 独占流：核对与补送

前提：该设备的序列只有你一个写入者。因此**可见状态就是你自己的提交历史**，
核对规则可以简化；但删除/保留是命名空间级运维动作，仍需检查。

### 3.1 状态机

```
构造批次(去重/新鲜now/限量) → 发送 → ┬─ 200 回执(S) → 读回核对 → 按核对结果计数
                                    ├─ 超时/断连   → 读回核对 → 缺的进补送批
                                    ├─ 409/422/400 → 未落库，按 1.5 分支处理
                                    └─ 不得直接计数、不得盲目重送
```

### 3.2 读回核对（reconcile）

对批次窗口 `[min_t, max_t+1)` 发 range，matchers 锁定该设备序列：

```http
POST /ridge/v1/spaces/backfill/range
{"start": 1000, "end": 3001, "matchers": [{"label": "node", "op": "=", "value": "edge-a"}]}
```

逐点比对批内 `(time, value)`：

- **值匹配** → 确认。独占流上没有第二个写入者，值匹配即你自己的提交（实录
  A2：批 #1 回执丢失，读回 3 个点值全对、同落一个 `sequence`，直接确认，
  **不重送**）。
- **缺失或值不符** → 先查本地尝试日志（是不是你自己后来改过），再查
  `GET .../deletions`（是否被删除掩盖，见 3.4），最后查 `floor`（是否已终态）。
  都不是 → 进入补送批。

### 3.3 计数规则

**新增量只来自读回核对，永不来自 `accepted`。**

- 发送前后各读一次，差集才是新增量。实录 A3：混合批 `{2000:已存在, 4000:新增}`，
  回执 `accepted=2`，读回差集只有 `4000` —— 新增量是 **1**。
- 持有回执时，用 `sequence` 精确归属：读回点的 `sequence == 回执.sequence`
  才是这一批写入的（A3 中 `2000` 和 `4000` 的 sequence 都等于新回执——
  `2000` 是被**重复提交**，不是新增）。
- 批内重复点会让 `accepted` 进一步失真（A4：`accepted=2`，可见 1 点）。
  旧客户端的 Accepted 计数器在实录全程累计 7，真实新增量是 **5**。

### 3.4 补送（repair batch）

- 补送批**只含核对后确认缺失的点**，不是整批重送。独占流上重送同值点虽然
  可见值幂等，但会推高 sequence、污染后续归属判断，并让 `accepted` 继续虚高。
- 被删除掩盖的点：删除不推进 floor，**可以重新接纳**。补送后读回确认
  `sequence > 墓碑.sequence`（实录 C1→C2：删除 `sequence=13` 掩盖 `2000`，
  补送后 `2000` 以 `sequence=14` 恢复可见）。
- 补送批为空就不要发请求（空 points 数组会被 422 拒绝）。
- 409 分支：
  - `namespace is read-only` → 停送等运维，稍后整批重试（未落库）；
  - `point precedes retention floor` → 这些点**终态不可补**，从批次剔除并记
    "retention 丢失"（依据只有你的本地日志，见第 5 节），其余点重发；
  - `point exceeds out-of-order time policy` → 命名空间 watermark 已超过
    `time + lateness_ms`，这些点**终态不可补**（watermark 只涨不跌），剔除
    后重发其余点；
  - `point exceeds future skew policy` → 刷新 `now` 重发。

## 4. 共享流：归因与交还上游

共享流上别的客户端随时可能修正同一 `(series, time)`，而接口是
last-wins：**你的重送会用更大的序号盖掉对方的修正**。实录 B0 演示了事故
本身：批次回执丢失（B0a）→ 对方把该点修正为 99（B0b）→ 旧客户端盲目整批
重送（B0c）→ 可见值变回陈旧值 20，对方的修正被静默覆盖。

因此共享流只有一条铁律：**回执丢失后绝不盲目重送；先读归因，无法归因的记
录交还上游。**

### 4.1 归因分类

对批次窗口读回（同 3.2），并取证据：`GET .../deletions`（墓碑）、
`GET /spaces/{space}`（floor、`last_sequence`）。逐点分类：

| 读回情况 | 分类 | 处置 |
| --- | --- | --- |
| 值匹配 且 `sequence ∈ 你持有的回执` | `confirmed_yours` | 计数 |
| 值匹配 但 `sequence` 不属于你（含回执丢失、你根本没有回执） | `unattributable` | **交还上游** |
| 值不匹配 | `superseded`（对方已修正） | **交还上游**，禁止重送 |
| 点缺失 且有覆盖该点的墓碑 | `absent_deleted` | **交还上游**（附墓碑证据；在共享流上不要擅自恢复别人的删除） |
| 点缺失 且无墓碑、`time ≥ floor` | `absent_unknown` | **交还上游**（可能是从未提交，也可能是删除后墓碑已被 compact 清掉，接口无法区分） |
| `time < floor` | `terminal_floored` | 终态，记入本地日志，不再交还也不再补 |

注意第二行：**值匹配不足以归因**。回执丢失时你不知道自己那次的
`sequence`，可见点可能是你的提交，也可能是对方写了相同的值——接口无法区
分（第 6 节的对照实验专门验证这一点）。

### 4.2 交还上游数据包

把无法归因/被压制/被删除的记录打包交还给上游（拥有跨客户端裁决权的系
统）。格式（实录 B4）：

```json
{
  "packet_version": 1,
  "space": "backfill",
  "collector": "collector-1",
  "batch_id": "B1",
  "observed_at_sequence": 11,
  "records": [
    {"labels": {"__name__": "pulse_total", "node": "edge-b", "zone": "east"},
     "time": 1000, "expected_value": 10,
     "classification": "unattributable",
     "observed": {"visible": true, "value": 10, "sequence": 11},
     "collector_receipts": [],
     "evidence": {"tombstones_covering": [], "floor": -4503599627370496}},
    {"labels": {"__name__": "pulse_total", "node": "edge-b", "zone": "east"},
     "time": 2000, "expected_value": 20,
     "classification": "superseded",
     "observed": {"visible": true, "value": 99, "sequence": 11},
     "collector_receipts": [],
     "evidence": {"tombstones_covering": [], "floor": -4503599627370496}}
  ]
}
```

纪律：

- 交还的记录**不计入你的新增量**，批次状态置为"部分核对"；
- 上游裁决前，不对这些点做任何写入（接口没有 compare-and-swap，你的任何
  写入都是 last-wins 覆盖）；
- 上游裁决后，只按裁决**定向重写**被授权的点。实录 B5→B6：上游裁定
  `1000` 处对方的相同值重报就是同一样本（在上游账本记账，采集端不重复
  计）、`2000` 的权威值是 20 → 采集端只发 `{2000: 20}` 一个点，读回确认
  `sequence == 新回执` 后才计 1 个新增量；`1000` 的可见 sequence 仍是对方
  的提交，采集端不计。

## 5. 删点与保留推进后，哪些回执结论仍可确认

| 事件 | 仍可通过接口确认 | 不再能确认 |
| --- | --- | --- |
| 写入提交于 S，之后无删除/保留 | 读回：点可见、`sequence == S`、值匹配；`GET space` 的 `last_sequence ≥ S`、`watermark` | — |
| 删除 D 覆盖你的点（S < D） | `GET .../deletions` 列出的墓碑（区间、序列、D）+ 本地日志中的回执 S ⇒ "已提交、后被掩盖"；D 之后重新接纳的点可见且 `sequence > D` | 被掩盖样本本身（任何读接口都看不到）；**compact/retention 之后连墓碑记录也被清空**（实录 C3、C4f），删除事件只剩本地日志可查 |
| 保留把 floor 推过 t | `floor` 字段（`GET space` 或任意 range 响应）：`t < floor` ⇒ **终态**：物理已删、写入必 409。floor 单调不减，该结论永久有效（实录 C4d/C4g） | 点的值与"是否提交过"——只剩你的本地日志；`watermark` 仍保留历史最大时间戳，可佐证"曾有写入被接受"，但不能对应到具体批次 |
| `seal` / `compact` | 逻辑可见点与**每点 sequence 完全保留**（实录 A5、C3），归属判断不受影响 | 物理布局（head/块）变化；compact 同时清空墓碑清单 |

推论：

- "已提交且仍可见"——读回 + sequence 相等即可确认，跨 seal/compact 有效，
  跨删除/保留失效。
- "已提交但被删除掩盖"——只在**下一次 compact/retention 之前**可经墓碑清单
  确认；之后只剩本地日志。
- "已提交但被保留回收"——点本身永远不可再确认；但"终态不可补"这个结论
  本身可以永久经 floor 确认。
- `accepted` 在任何时刻都不能确认为新增量。

## 6. 对照验证：可见值相同，提交历史不同

手册的核心禁令是**不把"现在读得到"当成"这次请求一定成功"**。实录 D 构造
三段提交历史不同、但可见值完全相同的序列（`edge-c`，`hist ∈ {h1,h2,h3}`，
都是 `500 → 10`）：

| 历史 | 提交过程 | 读回 |
| --- | --- | --- |
| h1 | 采集端写入，回执保留（seq 20） | `(500, 10, seq=20)` |
| h2 | 采集端写入但**回执丢失**（seq 21），对方随后写入**相同的值**（seq 22） | `(500, 10, seq=22)` |
| h3 | 采集端写入（seq 23）→ 运维删除（seq 24）→ 对方重新接纳相同值（seq 25） | `(500, 10, seq=25)` |

一次 range（实录 D4）读回三个 `(500, 10)`，肉眼无法区分。两条判定规则的
结果：

- **朴素规则**"读到的值 == 我发的值 ⇒ 我的请求成功"：三个历史全部确认，
  计 3 个新增量——h2 把对方的提交记到自己头上，h3 把"自己的提交已被删
  除、可见的是对方的重新接纳"误判为成功。
- **手册规则**（4.1 分类）：h1 `confirmed_yours`（seq 20 == 持有的回执）；
  h2 `unattributable`（回执丢失，seq 22 归属不明）→ 交还上游；h3 持有回执
  23 但可见 seq 是 25，且墓碑 24 覆盖该点（`23 < 24 < 25`，实录 D5 墓碑仍
  在清单中）→ 自己的提交已被掩盖，可见点不是自己的 → 交还上游。计 1 个新
  增量，2 条交还。

`replay.py` 对这三条历史分别断言了分类结果，并断言朴素规则与手册规则给
出不同结论——这就是"手册没有把读得到当成请求成功"的可执行证据。

## 7. 计数规则速查

| 规则 | 做法 |
| --- | --- |
| ✅ 新增量来源 | 读回核对的差集，或回执 `sequence` 与读回点 `sequence` 的精确匹配 |
| ✅ 超时/断连 | 标记结果未知 → 读回核对 → 独占流补缺失点、共享流走归因 |
| ✅ 共享流冲突 | 交还上游数据包，等裁决后定向重写 |
| ✅ 终态判断 | `time < floor`（保留）或超 `lateness_ms`（迟到水位）→ 剔除并记日志 |
| ❌ 禁用 | 把回执 `accepted` 当新增量 |
| ❌ 禁用 | 超时后整批重送（共享流上会覆盖他人修正；独占流上污染计数与归属） |
| ❌ 禁用 | 把"读回值 == 发送值"当作"这次请求成功"（第 6 节） |
| ❌ 禁用 | 在共享流上擅自恢复被删除掩盖的点（交还上游，附墓碑证据） |

## 8. 附录：重放方式

```sh
python3 examples/backfill/replay.py            # 需要 go 在 PATH；或 GO=/path/to/go
```

脚本在临时目录构建服务器、用全新的临时数据库完整跑完第 3–6 节的全部场景
（A 独占流核对与补送、B 共享流归因与交还、C 删除/保留后的可确认性、D 同
